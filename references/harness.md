# Harness 工程规范

> 阶段 1 就位、阶段 3 迭代实施时读取。用户无需懂这些，你自动执行。

## 五个角色，各管各的

让项目不乱的核心：**写代码的人不能同时是检查代码的人。**

| 角色 | 只做什么 | 不做什么 |
|------|----------|----------|
| 架构师 | 出设计文档 | 不写一行代码 |
| 开发者 | 按设计写代码 | 不改设计、不自测 |
| 测试员 | 写测试案例、跑测试 | 不修 bug，报告给开发者修 |
| 审查员 | 查架构合规 | 不改代码 |
| 调度员 | 路由任务、更新进度 | 不管业务 |

**降级说明**：如果当前宿主不支持子智能体（多 Agent 并行），就由你一个人在会话里「按角色切换」严格执行——关键检查一样不少，只是串行完成。不要让用户操心这件事。

## 文件交接

每个角色干完活，把产出写进 `phases/` 文件夹，不靠聊天记录交接、靠文件：

```text
架构师 → phases/01-design.md
    ↓ 开发者读这个文件
开发者 → 代码 + phases/02-impl.md
    ↓ 测试员读这个文件
测试员 → phases/03-test.md
    ↓ 审查员读这个文件
审查员 → phases/04-review.md
    ↓ 调度员判断能否完成
```

每次新会话打开文件就知道做到哪了。

## 五道门禁

每步干完必须通过检查，不通过不许往下走：

| 门禁 | 检查什么 | 谁查 |
|------|----------|------|
| Gate 0 | 需求说清楚了吗？ | 架构师 |
| Gate 1 | 设计文档完整吗？ | 调度员 |
| Gate 2 | 代码能编译吗？ | 开发者 |
| Gate 3 | 测试全过了吗？ | 测试员 |
| Gate 4 | 架构违规了吗？ | 审查员 |

## 防三个经典翻车

| 翻车 | 怎么防 |
|------|--------|
| 「帮我开发一个系统」——AI 一次想做太多 | 每次只做一个 feature，拆成独立小任务，做完一个再下一个 |
| 代码写完了就当完成了 | 五道门禁全过才算完成 |
| AI 写的测试和 AI 写的代码有同样盲区 | 测试员和开发者不能是同一个角色 |

## 代码质量重点

**后端**：服务可启动、配置可加载、接口返回格式统一、错误处理机制、日志规范、数据库连接与权限入口。

**前端**：目录结构分层合理、组件命名与复用规范、请求封装统一、状态管理策略明确。

## Harness 思想（始终遵循）

1. 任务分流、分布，避免死循环
2. 任务满足要求才可输出
3. 兜底机制
4. 成长维护，保证 agent 健康运行

## 发版评审会（可选，发版前）

项目准备发版（发布/上线）前，先问用户「是否需要发版评审会？」，由用户决定。

用户说需要 → 进入评审会流程：

1. 设置多个评审角色（如架构评审、代码评审、产品评审、安全评审、体验评审）+ 一个「集成评估师」。
2. 各角色对候选版本**互相挑刺、质疑**，找出问题。
3. team leader（总调度）**不参与辩论**，只做最终敲定。
4. 集成评估师汇总各方意见，形成结论：**可以发版 / 需要修改**。
5. 结论「可以发版」才进入部署/发布；「需要修改」则回到对应阶段修复，修复后重新评审。

**降级说明**：宿主不支持多角色并行时，由你一人依次扮演各评审角色，但「集成评估师」的汇总和「team leader」的敲定要分开做，不能自己评审自己敲定。
