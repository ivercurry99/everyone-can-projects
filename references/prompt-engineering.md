# 结构化提示词模板（Prompt Lock）

> 弱模型最容易出问题的一步：**"帮我做个项目"一句话 → Agent 直接乱写代码**。
>
> 本文件给出"锁死的 Prompt 结构"：**任何模型，只要按这个结构走，出来的立项/设计/进度都是一致、可恢复的。**
>
> 注意：本技能是"纯流程技能"——所有产出都是中文 Markdown。Prompt 用中文书写即可，不需要英文翻译。

---

## 1. 触发词检测（= 什么时候用本技能）

用户说以下任意一种，就启用 `everyone-can-projects`：

- 「帮我做个项目 / 网站 / App / 工具」
- 「vibe coding」「我想 vibe 一个」
- 「我想做一个 XXX」且描述了目标/功能，但没有现成工程骨架
- 「接着做上次的项目」（此时走恢复流程，不再问项目信息）

以下情况**不要用本技能**：
- 只是对现有小功能做一次改改（1~2 个文件内、且已有项目结构）
- 纯技术咨询（"Python 怎么写装饰器"）
- 用户本人就是资深工程师，明确说要走自有的开发流程

## 2. 立项阶段 Prompt 结构（阶段 0）

**强制顺序**：先问，再写文档；文档 7 件必须齐全。

```
你好，我会先快速帮你把想法变成可执行的项目。请确认以下信息（想不清的就跳过，我会用合理默认值）：

1) 项目名（比如：my-personal-site）：<回答>
2) 一句话简介（我想做什么）：<回答>
3) 核心模块 / 功能，用逗号分开（比如：文章列表, 生活记录, 社交按钮）：<回答>
4) 参考网站或风格（可选）：<回答>
5) 部署要求（可选，默认"暂不部署，先本地可用"）：<回答>
6) 其他补充（可选）：<回答>
```

收到答案后的内部操作（对用户透明）：

```
1. 执行 scripts/scaffold_project.py scaffold（或等价手动流程）
   --name <项目名>
   --brief <简介>
   --modules <模块,模块,...>
   [其他可选参数]

2. 检查 docs/planning/ 下 7 份文档齐全；把项目目录告诉用户。
3. 向用户总结："我已经按你的信息生成了 X，接下来将进入阶段 1（Harness 就位）。"
```

## 3. Harness 阶段 Prompt 模板（阶段 1）

```
现在进入：阶段 1 · Harness 就位。

我将按以下顺序帮你做好工程化准备：

A. 确认五角色分工（写进 docs/planning/03-project-dossier.md）
   架构师（出设计不写代码） / 开发者（写代码不改设计） / 测试员（测不修） / 审查员（查合规不改代码） / 调度员（路由+门禁）

B. 确认五道门禁（写进 docs/planning/07-engineering-norms.md）
   Gate0 需求清楚 → Gate1 设计齐全 → Gate2 可编译/可运行 → Gate3 测试通过 → Gate4 架构合规

C. 确认文件交接目录 phases/ 就位：01-design / 02-impl / 03-test / 04-review

如果当前宿主不支持子智能体并行：我会一人串行切换角色；门禁一项都不会少。
如果宿主没有记忆系统：使用项目根 PROGRESS.md 作为唯一事实来源。

以上内容请你确认是否 OK（默认 OK，有异议请指出）。
```

## 4. 每个 Feature 迭代模板（阶段 3）

**严格每次只挑一个 feature。** 调度员开场必须说：

```
当前 feature：<名字>（来自 docs/planning/02-feature-list.md 的第 N 项）
```

### 4.1 架构师 → phases/01-design.md

```
# 架构师：<Feature 名> 设计

1. 目标（完成标准 = 什么算做完）：
   ...

2. 影响范围（改哪些层、哪些文件）：
   ...

3. 数据结构 / 接口签名（如有）：
   ...

4. 不做什么（显式边界）：
   ...
```

### 4.2 开发者 → phases/02-impl.md + 代码

```
# 开发者：<Feature 名> 实现记录

- 改动文件：a.py, b.py, ...
- 按设计做了什么：
  1. ...
  2. ...
- 自测 smoke case（跑通的命令/证据）：
  $ <命令>
  → <关键输出>
```

### 4.3 测试员 → phases/03-test.md

```
# 测试员：<Feature 名> 测试报告

- 测试环境：
- 用例列表（至少覆盖主路径 + 2 条边界）：
  1. [PASS / FAIL] ...
  2. [PASS / FAIL] ...
- 结论：是否通过 Gate3
- FAIL 时：请开发者修复；修复后重测；不自己改代码。
```

### 4.4 审查员 → phases/04-review.md

```
# 审查员：<Feature 名> 架构审查

对照 docs/planning/07-engineering-norms.md 逐项检查：

- [ ] 分层正确（接口层 / 业务层 / 数据层 没混）
- [ ] 无魔法数字 / 无裸异常吞咽
- [ ] 输入有 Schema 校验（对外接口）
- [ ] 没有引入不需要的依赖
- [ ] 去 AI 味 6 项（见 references/fallback-strategy.md §2）全部勾过

结论：[通过 / 需要修改]
需修改时：列出具体改哪几处，开发者改完再次审查。
```

### 4.5 调度员：门禁签字

```
# 调度员 · <Feature 名> 门禁汇总

- [x] Gate0 · 需求清楚（有明确完成标准）
- [x] Gate1 · 设计齐全（phases/01-design.md 存在且有 4 节内容）
- [x] Gate2 · 代码可运行（有 smoke 证据）
- [x] Gate3 · 测试全过（测试报告结论通过）
- [x] Gate4 · 架构合规 + 去 AI 味（审查员通过）

门禁结论：✅ 通过 / ❌ 回到 <哪一步>
```

**调度员签完字，才算这个 feature 完成。** 没签字就不算，不许进入下一个 feature。

```
  <具体动作>
```

## 6. 发版评审模板（阶段 5，可选）

```
是否需要发版评审会？（y/n，默认 n）
```

用户说需要时：

```
进入发版评审会：
  角色：架构评审 / 代码评审 / 产品评审 / 安全评审 / 体验评审 + 集成评估师（汇总）
  Team Leader：只做最终敲定，不参与辩论。

各角色请依次质疑候选版本（互相挑刺，别给面子）。
集成评估师汇总意见，给出「可以发版 / 需要修改」。
Team Leader 根据汇总最终敲定。
```

## 7. Prompt 稳定性硬约束

1. **任何一个模板里的 checklist 项目少一条就不算完成。**
2. **文件写完才算完成**：聊天里说"我写了"不算，`Path(...).is_file()` 为真才算。
3. **调度员签字是最后一道闸**：没签，坚决不进下一阶段。
4. **用户模糊就用默认值**：绝不连续追问同一问题超过 1 次；默认值要在对用户的总结里明确告诉用户"我做了这些假设"。
